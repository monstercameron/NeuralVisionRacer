# Technique report: Triangle Splatting

**Research focus:** triangle/surface representation as an alternative to Gaussian splats in NeuralVisionRacer.
**Recommendation:** prototype offline conversion/rendering on a small static asset; defer a runtime renderer replacement. A separate triangle pass is promising for assets that can become opaque geometry, but current assets, visuals, animation, and sorting are not compatible by a drop-in switch.

## Exact technique and representation

The paper is **“Triangle Splatting for Real-Time Radiance Field Rendering”** by Held et al., accepted to 3DV 2026, first posted as arXiv:2505.19175 in May 2025. Do not confuse it with the separate 2025 **2D Triangle Splatting (2DTS)** paper. Triangle Splatting directly optimizes an unstructured “triangle soup”: each primitive has three independently movable 3D vertices, one color, opacity, smoothness parameter σ, and spherical-harmonic appearance during training. It projects each triangle, computes the maximum of three signed edge half-plane distances (an SDF), and applies a normalized smooth window function to soften coverage at the edges. Contributions are alpha blended in depth order. During final optimization, opacity and σ are annealed and SH is set to zero to yield solid triangles for ordinary mesh rendering. The triangles are not guaranteed to be connected into a watertight manifold mesh.

Primary sources: [paper (arXiv HTML)](https://arxiv.org/html/2505.19175), [project page](https://trianglesplatting.github.io/), [official source repository](https://github.com/trianglesplatting/triangle-splatting). The project page says the engine demo had no shaders and was not specifically trained for game-engine fidelity; that is a material limit on treating its exported scene as an equivalent replacement for the current image-based renderer.

## What the authors measured

The paper’s representation-level comparison reports 97 FPS / 795 MB for Triangle Splatting versus 64 FPS / 484 MB for 2DGS, on an NVIDIA A100 evaluation setup; the authors describe TS as 40% faster than 2DGS. This is not the same setup as the striking mesh-renderer result. In a separate conventional mesh-renderer experiment on Garden (about 2 million triangles), the paper reports 2,400 FPS at 1280×720 / 1,900 Full HD / 1,050 4K on Linux RTX 4090; RTX 5000 Windows numbers are 570 / 380 / 290 FPS at HD / Full HD / 4K, and MacBook M4 macOS numbers are 500 / 370 / 160. These are authors’ numbers, not browser measurements. The mesh demo explicitly omits shaders and is not trained for game-engine fidelity. Do not transfer any of these rates to this WebGPU engine or compare them directly to its benchmark.

The paper reports sharper detail and improved perceptual LPIPS against 2DGS/BBSplat on Mip-NeRF360, but notes a PSNR tradeoff on an example (18.41 vs 2DGS 21.27). It says TS is especially effective on indoor and structured outdoor scenes; sparse/ambiguous outdoor scenes can produce view-specific floaters. Sources: [paper experiments and limitations](https://arxiv.org/html/2505.19175), [paper project page](https://trianglesplatting.github.io/).

## Fit to this engine

The current production format is SOG V2, with WebP streams for positions, rotations, scales, base color, SH labels/centroids and codebooks. The renderer has a GPU radix sort of splat-center depths, indexed 4-vertex/6-index quads, a color blend pass and a depth prepass. Current levels peak at roughly 2.35M Saburi and 5.15M Delft resident splats; the car has 648,207 splats. Wheel centers are deformed by compute while orientations and SH retain wheel-part transforms. The engine includes SH appearance, car lights/sharpening, shadow proxy, streaming LOD/chunk fades and voxel/Rapier collision. See [performance.md](../../performance.md), [optimization session](../../optimization-session-2026-10-26.md), [scene.rs](../../../crates/splat-render/src/scene.rs), [sort.rs](../../../crates/splat-render/src/sort.rs), and [sog.rs](../../../crates/splat-render/src/sog.rs).

### Assets and conversion

- Existing SOG assets cannot be reinterpreted as Triangle Splatting data: Gaussian center/scale/quaternion/color/SH codes do not contain triangle connectivity or three optimized vertices. The official pipeline trains triangle soups from posed image collections; a conversion would require an offline reconstruction/retuning stage from source photos or explicit mesh extraction and appearance baking. It is not a lossless SOG-to-triangle conversion.
- Current static scanned environments are better candidates than the car. The car needs animated wheels, view-dependent highlights, and a transition between body and wheel coordinate systems. The paper’s game-engine output uses SH=0/opaque faces, so it will not preserve current SH-driven/view-dependent appearance or transparency as-is.
- A triangle mesh could be uploaded using ordinary WebGPU vertex/index buffers and drawn through the portable raster pipeline. No CUDA is needed at runtime. The research training implementation uses Python 3.11/CUDA 12.6 and custom kernels; offline training may use CUDA, but portability work is required only for an exporter, not for runtime.

### Runtime costs and likely tradeoffs (inference)

- **Sorting:** opaque triangles with depth writes can avoid the global per-frame back-to-front sort. This is the most plausible engine-level gain. But the differentiable TS training representation uses alpha blending and paper methodology orders contributions by depth, so semitransparent raw TS still needs compositing. The high FPS result is specifically the final annealed opaque mesh. The game can only realize the sorting win if conversion yields robust opaque geometry and the engine’s inter-object/foreground semantics are retained.
- **Rasterization/overdraw:** triangles use the GPU’s conventional triangle path and hardware clipping/depth testing. Opaque surfaces can depth-reject hidden fragments, but 2M/5M+ resident triangles are a large vertex/primitive workload, and fine face tessellation can increase vertex processing. A mesh may trade current full splat sort and translucent overdraw for conventional vertex and fragment work. Browser GPU results must decide which side wins.
- **Memory and LOD:** compact positions plus shared indices might reduce per-primitive payload versus SOG’s attributes, but the triangle format duplicates three positions unless indexed/shared across faces; triangle soup has three vertices per primitive and the official output is triangle-level color/opacity. The paper’s A100 model memory (795 MB) is larger than 2DGS/3DGS model numbers, while its exported mesh benchmark does not report browser asset/GPU memory. It does not demonstrate smaller streaming payloads. Keep existing streamed SOG LOD until offline mesh LOD export demonstrates equal visual quality and lower resident/upload cost.
- **Lighting/shadows/collision:** explicit geometry naturally supports normal-based lighting, depth/shadow passes, and mesh collision, but this specific learned TS mesh has no validated dynamic relighting fidelity: its game-engine demo has no shaders, and SH is forced to zero for final opaque export. It might improve collision only after topology cleanup; triangle soup is not necessarily watertight or manifold. Wheel rigging could skin/transform its wheel submeshes, but that requires explicit part classification and new vertex deformation; it is not compatible with current per-splat GPU wheel deformation.

### Feasibility and license

Rust/WASM/WebGPU can draw conventional triangles, with a WebGPU vertex/index-buffer path; implementing such a path is technically feasible. A new asset schema/importer, mesh construction and streaming LOD policy are required. The official training repository is Apache-2.0, and its README specifies CUDA 12.6 and custom CUDA kernel compilation. The technique’s paper/project page use CC BY-SA for the site, while the repo code states Apache-2.0; confirm bundled submodule licenses independently before reusing any code or model files. Runtime could be implemented independently in Rust/WGSL and need not depend on the CUDA trainer.

## Smallest useful prototype and acceptance gates

1. Produce or obtain one small official Garden/Room Triangle Splatting export; do not touch the production SOG files. Export to a minimal Rust-readable position/index/color asset and render it with a standalone WebGPU triangle pass in the existing application shell.
2. Compare against the same camera/reference views at the same canvas size and effects settings. Include an opaque depth-write pass and (only if required) an alpha-blended variant. Measure in-browser GPU timestamp spans, CPU submission and upload/resident bytes, using the existing benchmark harness and identical scene/camera.
3. Prototype against static Garden-like scenery first; do not infer suitability for the moving car from the static model. Then test a single wheel/body assembly only if a fitting explicit mesh and usable part labels are available.

**Success gate to expand:** visually acceptable view comparisons (including thin geometry, occlusion, shadows, drive-through edges and fast camera movement); stable non-cracked surface geometry; no broken streamed LOD transitions; runtime remains WebGPU-portable; and a repeatable whole-frame improvement against the same production-scene baseline that outweighs added upload/memory and asset preparation. For a sorting-removal test, require opaque geometry and verify depth ordering among level, car and other rendered objects.

**Recommendation:** **prototype** as a possible opaque static-scene path, especially if off-line mesh reconstruction also benefits shadows/collision. **Defer** replacing SOG broadly and the dynamic car. The 2,400-FPS result is a strong feasibility signal for conventional mesh rendering, not a predicted optimization for this browser scene.
