# Technique report: Octree-GS LOD-structured anchors

**Source technique:** *Octree-GS: Towards Consistent Real-time Rendering with LOD-Structured 3D Gaussians* (Ren et al.; TPAMI 2025; initial paper arXiv:2403.17898). Primary sources: [paper](https://arxiv.org/abs/2403.17898), [official project](https://city-super.github.io/octree-gs/), [official code](https://github.com/city-super/Octree-GS). A follow-on [Octree-AnyGS](https://github.com/city-super/Octree-AnyGS) extends the anchor framework to explicit 2D/3D Gaussians and Scaffold-GS. Reviewed 2026-10-26; GitHub links refer to current default branch, not a pinned commit.

## What it does

This is a trained, anchor-based representation. It builds an octree from SfM points, determines the number of levels from the near/far depth quantiles of training views, and assigns anchors to levels so Gaussian support scales with expected projected footprint. It uses a neural parameterization (Scaffold-GS style MLPs predicting color/covariance/opacity from anchors), adaptive anchor growth/pruning and a learned per-anchor LOD bias to recover high-frequency detail between discrete levels. Progressive coarse-to-fine training encourages distinct roles for each LOD. At runtime the camera selects appropriate LOD anchors, so distant views process fewer Gaussian primitives. This is not a generic preprocessing pass over an arbitrary finished SOG.

Primary details: [Octree construction and depth-derived levels](https://arxiv.org/abs/2403.17898) (Sec. 4.1), [adaptive growth/pruning and LOD bias](https://arxiv.org/abs/2403.17898) (Sec. 4.2), [progressive training](https://arxiv.org/abs/2403.17898) (Sec. 4.3), [paper repository/results](https://github.com/city-super/Octree-GS).

## Performance and quality evidence

On the MatrixCity benchmark, the authors report 2K-resolution rendering averages of 45.82/46.30/47.57 FPS for three novel-view trajectories (T1/T2/T3), against Mip-Splatting 12.35/10.13/11.41 and Scaffold-GS 3.22/4.52/4.98. For Block_All, reported model counts are 665K versus 694K for Mip-Splatting and 930K for Scaffold-GS, with PSNR 26.41 versus 24.28 and 26.34 respectively. The paper describes roughly 10x rendering speed over state-of-the-art in large-scale/extreme-view sequences. The benchmark is reported at 2K image resolution; the arXiv paper text consulted does not state the GPU model for these figures. Dataset and renderer are CUDA-side academic benchmark setup; the paper's FPS does not establish browser/WebGPU gains, and per-view visible counts/details/settings are not a same-engine comparison. [Paper Table 3 and discussion](https://arxiv.org/abs/2403.17898).

On multiscale BungeeNeRF, Octree-GS reports an average of 1.395M primitives versus 2.571M standard 3D-GS and 1.666M Scaffold-GS, with average PSNR/SSIM/LPIPS 28.21/0.922/0.088. It maintains 539K/1160K/1879K/1615K primitive counts across four scales compared to standard 3D-GS 502K/1239K/4212K/5462K; this illustrates its strongest advantage at wide scale and a tradeoff that it can use more at near scale. These are representation/training results, not transferable engine costs. [Paper Table 2](https://arxiv.org/abs/2403.17898).

## Fit against NeuralVisionRacer today

The current engine already has the core operational behavior Octree-GS is meant to support: SOG V2 author-provided multi-LOD levels partitioned into spatial leaves; screen-space error selection; per-leaf frustum/distance prioritization; a shared fixed pool; hysteresis/retention; upload budgets; fades, cache, prefetch; global sort. It already applies LOD to surroundings while car assets remain separate, with the user's priority to tune LOD against the game camera. Replacing this with Octree-GS's neural anchors and parameter MLP would duplicate existing multi-LOD data and substantially replace content authoring/decoding/shading, not be an incremental hierarchy upgrade.

Possible transferable lessons are narrow: derive LOD levels from camera-depth/footprint distributions for asset preprocessing rather than fixed level spacing, test view/scale-aware anchor density, and use image-space multi-scale quality metrics to tune current selection thresholds. The existing `lod_error_px` selection is already screen-space-based, making raw distance tuning alone less novel. If existing level payloads lack visual consistency at transitions, learned LOD bias is a potential asset-training idea, but it requires retraining/finetuning the representation and source images. Octree-GS's output is not directly SOG V2: checkpoints are `.ply` anchor points plus PyTorch color/covariance/opacity MLPs (and optional appearance embeddings) per repository docs. Octree-AnyGS may support explicit 3DGS primitives, but that does not imply existing SOG chunks can be imported unchanged or keep their learned cross-LOD consistency.

A browser implementation could port the octree traversal and level assignment in CPU Rust or WGSL, but the core learned-anchor model needs a neural inference path and shader/storage budget; the official code uses CUDA 11.6/PyTorch and the reference viewers, so it is not portable as-is. Converting trained outputs into expanded explicit splats would lose some compactness and reintroduce expanded data/sort costs. Runtime anchor feature generation costs also need measuring. The paper focuses on scene imagery and does not provide evidence for animated car geometry; keep the car at its existing representation/LOD. LOD selection, transient overlap/fades, and global sort must be measured with the current car/state active, not hidden by disabling them.

## Memory, lifecycle and licensing

Octree-structured anchors can reduce the *view's* rendered Gaussian count, particularly as scale changes; they do not automatically reduce simultaneous resident bytes unless the representation itself is stored compactly or streamed. Current SOG streams only needed chunk levels into a reusable pool and decodes/uploads at most one texture per browser frame, so an expanded explicit export could worsen memory/network/upload/sort even if on-screen count improves. Conversely, a compact learned representation could lower bytes but needs a new decoder/shader and likely model weights. The reference project reports a CUDA server (Ubuntu 18.04, CUDA 11.6, gcc 9.4); no WebGPU portability claim is made.

The repository says to follow the original 3D-GS license rather than shipping an independent permissive license; check current `LICENSE.md`, submodule licenses, and model/data rights before reuse. Treat as research-only pending review. [Repository license note and expected checkpoint layout](https://github.com/city-super/Octree-GS).

## Smallest useful prototype and gates

1. Do **not** port the neural anchor renderer first. Use the existing levels and saved camera paths to audit per-level visible counts, quality, upload bytes, transition churn and global-sort input. Compare the current screen-space threshold selection against a proposed depth/footprint-derived schedule with unchanged image-quality target.
2. If this audit shows a genuine representation gap (rather than tuning), train one static small level with Octree-AnyGS/Octree-GS from available source images, export a small explicit 3DGS set, then convert to the current SOG path only if all attributes survive. Leave car/wheels/state untouched.
3. Acceptance: equal resolution/effects/car detail and no worse reference images (quantify PSNR/SSIM and inspect road markings/building edges), a clear visible-splat reduction at the matched quality target, fewer or equal bytes resident/uploaded, and repeated WebGPU pass-time improvement above noise. Capture p50/p95 GPU time, active splats, coverage, sort work, memory and transition peaks. No CUDA FPS extrapolation and no lower-detail comparison masquerading as an optimization.

## Recommendation

**Defer full Octree-GS adoption.** Its core contribution is a retrained anchor/neural representation, while this game already has streamed spatial multi-LOD leaves and a screen-space selector. First tune and validate the existing SOG LOD thresholds and inspect count/quality curves. Revisit Octree-AnyGS only if a measurable quality or asset-size gap remains and the original training images are available; the conversion, license, and WebGPU model-inference costs currently outweigh likely incremental gains.
